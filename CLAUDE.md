# Foodly Planner

Weekly meal planner: users get food suggestions based on their preferences and pick foods for each day/meal of their week.

Stack: React 19 + TypeScript + Vite 8 + Tailwind CSS v4 + TanStack Router (file-based, client-side only, no SSR) + TanStack Query. Backend on AWS (one Lambda + API Gateway HTTP API with a Cognito JWT authorizer, DynamoDB, Bedrock for AI; defined with AWS CDK in `infra/`, deployed with `npx cdk deploy`; the Cognito User Pool stays in the console), region `eu-west-2` (London).
Requires Node ≥ 20.19 (Vite 8).

## Project structure

Single package: frontend, backend, and shared code live in one repo with one `package.json`.

```
src/                      ← React frontend (client-side rendered)
├── routes/               ← TanStack Router file-based routes: each file is a URL
│   ├── __root.tsx        ← layout around every page
│   ├── _guest.tsx        ← layout for auth pages (illustration + form panel);
│   │                       guard: already signed in → redirect to /
│   ├── _guest/           ← public pages; "_guest" is not part of the URL
│   │   ├── sign-in.tsx          → /sign-in
│   │   ├── sign-up.tsx          → /sign-up
│   │   ├── confirm-email.tsx    → /confirm-email
│   │   └── forgot-password.tsx  → /forgot-password
│   ├── _authenticated.tsx ← guard: not signed in → redirect to /sign-in
│   └── _authenticated/   ← pages behind login; "_authenticated" is not part of the URL
│       ├── index.tsx            → /  (redirects to /plan-questions)
│       ├── weekly-plan.tsx      → /weekly-plan  (the planner)
│       ├── plan-questions.tsx   → /plan-questions  (questions about the week → AI → meal suggestions)
│       └── preferences.tsx      → /preferences  (planned)
├── routeTree.gen.ts      ← generated by TanStack Router; never edit
├── api/                  ← code that talks to outside services, one folder per service
│   └── auth/             ← Cognito calls, auth errors, token manager
├── components/           ← all React components (routes/ only does routing); styles live in each .tsx
│   ├── ui/               ← generic building blocks used anywhere (text-field/…)
│   ├── auth/             ← components for the auth pages (sign-in-form/…)
│   ├── weekly-plan/      ← the planner (grid, suggestions, meal cards, recipe dialog)
│   ├── plan-questions/   ← the plan questions flow (questions → AI → review)
│   └── <area>/           ← later: preferences/…
├── hooks/                ← shared React hooks, kebab-case files (use-form.ts: form state + validation)
├── lib/                  ← other frontend helpers used by 2+ routes (formatting…)
├── test/setup.ts         ← runs before every component test (jest-dom matchers, cleanup)
├── index.css             ← design system entry: imports Tailwind and the files in styles/
├── styles/               ← global styles only: theme.css (tokens), fonts.css, base.css,
│                           recipes/ (shared styling classes: buttons, card, auth background)
└── main.tsx              ← creates the router and QueryClient, renders the app
infra/                    ← AWS CDK: foodly-stack.ts describes the tables, Lambda, API (decision 24)
server/lambda/            ← the one Lambda for all routes (decision 18), bundled by CDK from here
├── index.mjs             ← entry: switches on the route, validates, reads/writes DynamoDB
├── data/                 ← the one DynamoDB client (db.mjs) and the cached meals list (meals.mjs)
├── suggest/              ← suggestion scoring (plain code, unit-tested)
├── understand/           ← AI: turns the user's text into answers (Bedrock)
└── recipe/               ← AI: writes a meal's recipe once and saves it
shared/                   ← types and validation used by both src/ and server/
└── validation/           ← pure rules, one folder each (email/email.ts, password/password.ts);
                            each returns an error message or undefined
```

- **Route files stay thin and only do routing:** the `Route` definition, the page heading and text, and the components that make up the page. All other UI, including forms and their state and logic, lives in `src/components/`: `ui/` for generic building blocks used anywhere (`ui/text-field/`), and one folder per area of the app for the rest (`auth/sign-in-form/`, later `weekly-plan/`, `preferences/`). Don't put components inside `src/routes/`.
- **UI pieces vs. a flow component:** components that show something (`PlanWizard`, `PlanReview`) only take props and report back with callbacks (`onDone`, `onConfirm`); they don't call APIs or navigate. One **flow** component per workflow (`PlanQuestionsFlow`) owns the API calls (`useMutation`/`useQuery` with functions from `src/api/`), loading and error states, and navigation (`useNavigate` + `ROUTES`). The route file only renders the flow.
- Routes don't import from each other; share through `components/`, `lib/`, `api/`, or `shared/`. Components in one area folder may use `ui/`, but not another area's components; if two areas need the same component, move it to `ui/`.
- Calls to outside services (Cognito, our backend) live only in `src/api/`. Routes call these functions; they never use the AWS SDK or `fetch` directly.
- **API function names say what they do:** verb + what it returns. `fetch…` reads from the server (`fetchMeals`, `fetchWeekPlan`), `save…` stores (`savePlanSlots`, `savePlanAnswers`), and an action verb when the server does work (`extractPlanAnswers`, `fetchOrGenerateRecipe`). Auth functions keep Cognito's action names (`signIn`, `confirmForgotPassword`).
- Backend data is loaded and saved through TanStack Query. Query functions and query keys live in `src/api/<service>/`; routes use them in loaders and components. Query does not handle tokens: the API client adds the access token, and the token manager refreshes it.
- **Page URLs come from `ROUTES` in `src/lib/routes.ts`** (`<Link to={ROUTES.planQuestions}>`, `navigate({ to: ROUTES.signIn })`, `redirect({ to: ROUTES.weeklyPlan })`), never from path strings. Add a new page there; `satisfies` checks each path exists in the router. Exception: the id in `createFileRoute('/_authenticated/plan-questions')`, which the router plugin writes and checks itself.
- Pages that need login go inside `_authenticated/`, so the `_authenticated.tsx` guard protects them. Auth pages (sign in, sign up…) go inside `_guest/`. A `_name.tsx` file is a layout route with no URL of its own: it renders an `<Outlet />` for the pages in `_name/` and can guard them in `beforeLoad`. Login state and the QueryClient are passed to routes through the router context.
- **Components: one folder per component**, named in kebab-case, with a file of the same name: `src/components/ui/text-field/text-field.tsx`, `src/components/auth/sign-in-form/sign-in-form.tsx`. The component itself is a PascalCase named export (`export function TextField`). No `index.ts` re-export files: import the file directly. Files that belong to one component (e.g. a later `sign-in-form.test.tsx`) go in its folder. This includes small helper components: no second component inside a component's file, even a private one; give it its own folder (in the same area, or `ui/` if it's generic).
- **Imports:** use `./` only for a file in the same folder (`./text-field`). Everything else uses a path alias: `@/` for `src/` (`@/components/ui/text-field/text-field`, `@/hooks/use-form`) and `@shared/` for `shared/` (`@shared/validation/email/email`). No `../` imports. Aliases are defined once in `tsconfig.app.json` (`paths`); Vite and Vitest read them via `resolve.tsconfigPaths`.
- `src/` never imports from `server/`, and `server/` never imports from `src/`. Both may import from `shared/`.
- Backend: `index.mjs` imports the feature folders (`suggest/`, `understand/`, `recipe/`); they never import `index.mjs` or each other, only `data/`. Table names and the model id come from `process.env`, set in `infra/`. Change AWS resources only in `infra/`, never in the console (drift).

## Testing

Vitest runs all tests (`npm test` to watch, `npm run test:run` once). Two projects in `vite.config.ts`:

| Project     | Files                              | Environment            | For                                                                     |
| ----------- | ---------------------------------- | ---------------------- | ----------------------------------------------------------------------- |
| `unit`      | `{src,shared,server}/**/*.test.ts` | `node`                 | Plain functions: validation rules, form logic, helpers, Lambda handlers |
| `component` | `src/**/*.test.tsx`                | `jsdom` (fake browser) | React components, with Testing Library + user-event + jest-dom          |

- Test files sit next to the file they test (`text-field/text-field.test.tsx`).
- Keep logic in plain functions so it can be unit-tested without React; keep components thin.
- Test behavior, not implementation: find elements the way users and screen readers do, preferring `getByRole`, then `getByLabelText`, then `getByText`. Avoid `getByTestId`. A test that can't find a field by its label means the label is broken.
- Simulate users with `userEvent.setup()` (`user.type`, `user.click`, `user.tab`), not `fireEvent`.
- Never call real Cognito or the backend in tests: mock `src/api/` functions with `vi.mock`.
- Every component test file has one axe test of the component's richest state (hint and error shown, dialog open…): `await expectNoAxeViolations(container)` from `@/test/axe`, in a test whose name contains "axe" (CI's "Accessibility (axe)" step selects them with `vitest run -t "axe"`) (`baseElement` for content portaled to `<body>`). jsdom can't measure color contrast, so that rule is off there.
- **Test critical scenarios, not coverage.** Write a test where a bug would leave the user stuck or misled (signing in, the plan questions flow, placing a meal, errors and limits); one test can walk a whole scenario. Plain markup, and what a library or another test already covers, needs no test of its own.
- Import test functions explicitly (`import { describe, expect, it } from 'vitest'`); no globals.

## Design system

All styling goes through the design system: [src/index.css](src/index.css) imports the tokens (`src/styles/theme.css`), fonts, base styles and recipes (`src/styles/recipes/`). It is the single source of truth — read it before writing UI code.

### Rules

- **Use only design tokens.** Tailwind's default palette is removed, so classes like `bg-red-500` or `text-gray-600` do not exist. Never use arbitrary values (`bg-[#fff]`, `p-[13px]`, `text-[22px]`) or inline `style` for colors, spacing, radius, or type.
- **Recipe or component?** If only **styling** is shared, use an `@utility` recipe in `src/styles/recipes/` (`btn-primary`, `card`): it works on any element, e.g. `btn-primary` on both a `<button>` (an action) and a `<Link>` (navigation). If **HTML structure or behavior** is shared too, make a component in `src/components/` (`<TextField>` renders the label, input, hint and error and links them with `aria-describedby`).
- **Component styles live in the component.** A component's utilities go in its `.tsx`; variants use a plain object map in the same file. No separate CSS file per component.
- **Use a recipe or component before composing utilities**, and only add layout utilities on top (`btn-primary w-full`, `card space-y-4`, `<TextField className="…">`).
- **Repeated pattern → recipe or component.** If the same group of utilities appears in 2+ places, add a recipe (styling only) or a component (structure too), following the rule above.
- **New color/size needed → new token.** Add it to the `@theme` block in `src/styles/theme.css` with a semantic name (what it's for, not what it looks like: `danger`, not `red`). Check that text colors meet WCAG AA contrast (≥ 4.5:1 on `canvas` and `surface`; ≥ 3:1 for UI borders/icons).
- **Single light theme.** Do not add dark mode or `dark:` variants.
- **No component libraries** (MUI, Radix, shadcn, Headless UI…). Components are hand-written to practice accessibility.

### Handled globally — don't repeat per component

- Focus ring on every `:focus-visible` element. Don't remove outlines (`outline-none`) unless replacing them with an equally visible style.
- Pointer cursor on every enabled `<button>` (disabled buttons keep `cursor-not-allowed` from the `btn` recipe).
- Reduced motion: animations/transitions are disabled under `prefers-reduced-motion`.
- Body background, text color, and font.

## Accessibility

Accessibility is a learning goal of this project; components must be accessible by construction.

- Prefer native elements (`<button>`, `<dialog>`, `<select>`, `<label>`) over ARIA. Add ARIA only when no native element fits, following the WAI-ARIA Authoring Practices Guide pattern.
- Every input has a `<label htmlFor>`; link hints/errors with `aria-describedby`.
- Buttons always have `type`. Clickable things are `<button>` or `<a>`, never `<div onClick>`.
- Keep the 44px minimum target size (`min-h-11`) on buttons, inputs and other controls.
- Use one `<h1>` per page and don't skip heading levels; name sections with `aria-labelledby`.
- Images have meaningful `alt`, or `alt=""` if decorative.
- Anything done by drag-and-drop must also be possible with keyboard/buttons.
- Status updates (e.g. "Added to Monday dinner") use a live region (`role="status"`).
